# UX/UI Audit — Durian Hub — 2026-11-11

**อัปเดต:** ผู้ใช้อนุมัติและปรับปรุงทั้งผู้ใช้/แอดมินแล้ว ดู [ผลแก้ไขและการตรวจซ้ำ](ux-ui-improvements-2026-11-11.md) ข้อค้นพบด้านล่างเป็นหลักฐานก่อนแก้ไข

## ข้อสรุป

พื้นฐานดีบน desktop: สีและธีมมีระบบ ฟอร์มมี labels ปุ่มหลักเด่น และ dialog
หลายตัวรองรับคีย์บอร์ด แต่ยังไม่ควรสรุปว่าพร้อมใช้งานทุกอุปกรณ์
จุดที่ต้องแก้ก่อนคือหน้าสนทนาและตารางแอดมินบนมือถือ ความหมายของคะแนนรีวิว
และการแยกข้อมูลจริง/ข้อมูลสำรอง/การโหลดผิดพลาด

รายงานนี้เป็นการตรวจ ไม่ใช่การแก้ application source หรือการรับรอง WCAG ทั้งระบบ
ใช้แนวทาง Impeccable audit/critique ประกอบการอ่านโค้ดและตรวจ UI จริง
ไม่ได้ใช้ Impeccable engine detector เนื่องจาก launcher ดาวน์โหลด engine ไม่สำเร็จใน session ก่อนหน้า

## สภาพแวดล้อมและวิธีตรวจ

- URL: `http://localhost:3000/` และ `/admin`; Edge บน Windows
- ตรวจที่ zoom 100% และ device emulation ผ่าน DevTools: 320px, 390×844,
  768×1024 และ 1440×900 ตามหน้าที่ระบุในตาราง ไม่ใช่ทุกหน้าคูณทุกขนาด
- ใช้หน้าต่าง InPrivate แยกเพื่อตรวจผู้เยี่ยมชม โดยไม่ออกจากบัญชีเดิม
- เปลี่ยน light/dark, เลื่อนหน้าและตาราง, ค้นหาไม่พบ, เปิด dialog, ทดลอง Tab/Escape
- ทดสอบ offline เฉพาะ InPrivate ด้วยข้อมูลสมมติ ไม่ใช่บัญชีจริง
  ยืนยัน `No throttling` และล้างข้อมูลสมมติก่อนปิดหน้าต่างทดสอบ
- คืนหน้าต่างหลักสู่หน้าแรก โหมดมืด zoom 90% ตามสภาพก่อนเริ่มตรวจ
- การเปิดห้องสนทนาเป็นการอ่าน ไม่มีการส่งข้อความ กด quick reply ปิดดีล
  สมัครสมาชิก ส่ง OTP หักคะแนน มอบสิทธิ์ ระงับบัญชี หรือลบข้อมูล
- หลักฐานภาพและ accessibility tree อยู่ในผล Computer Use ของบทสนทนานี้
  ไม่ได้บันทึกภาพที่มีข้อมูลสมาชิกลง repository

## Findings เรียงตามความสำคัญ

### P1 — ควรแก้ก่อนปล่อยให้ใช้งานจริงในวงกว้าง

**U01 · ปุ่มคำสั่งในห้องสนทนามือถือบีบจนอ่านยาก — ยืนยันจาก UI**

ที่ 390×844 ปุ่มตกลงราคา ดูประกาศ แจ้งปัญหา และรีวิวถูกวางในแถวที่แคบ
ข้อความแตกเป็นแนวตั้งหลายบรรทัด ทำให้หัวห้องสูงและพื้นที่ข้อความน้อย
แนวทาง: แยก action หลักหนึ่งตัว วาง action รองในเมนู/แถวที่จัดรูปใหม่ และคงทางเข้าช่วยเหลือที่เห็นชัด
ไฟล์: `src/app/page.tsx` ส่วนหัวห้องตั้งแต่ประมาณบรรทัด 4155

**U02 · ตารางสมาชิกแอดมินไม่เหมาะกับมือถือ — ยืนยันจาก UI**

ชื่อและคะแนนแตกหลายบรรทัด ต้องเลื่อนแนวนอนเพื่อเห็นคำสั่ง
และสูญเสียบริบทว่าแถวคำสั่งนั้นเป็นของใคร ปุ่มหักคะแนนอยู่ชิดกัน
แนวทาง: ใช้การ์ดสรุปบนมือถือพร้อมเปิดรายละเอียดสมาชิก ส่วน desktop คงตาราง
หากยังใช้ตาราง ให้ยึดคอลัมน์ระบุตัวสมาชิกและเพิ่มพื้นที่กดคำสั่ง
ไฟล์: `src/app/admin/page.tsx:1405` และส่วนปุ่มตั้งแต่บรรทัด 1478

**U03 · แสดง 5.0 ให้สมาชิกที่ยังไม่มีรีวิว — ยืนยันจาก UI และโค้ด**

เห็นทั้งหน้าหลักและตารางแอดมิน แอดมินใช้ `Number(u.ratingAvg ?? 5)`
จึงแสดงเหมือนมีคะแนนความพึงพอใจเต็มทั้งที่ยังไม่มีหลักฐานรีวิว
แนวทาง: เมื่อ count เป็น 0 แสดง “ยังไม่มีรีวิว” แยกคะแนนความประพฤติออกจากดาวคู่ค้า
ไฟล์: `src/app/admin/page.tsx:1474`, หน้าหลักและการแสดง rating ใน `src/app/page.tsx`

**U04 · แหล่งและความสดของราคายังแยกไม่ชัด — UI + code-level finding**

ค่าราคาเริ่มจาก `REGIONAL_SEASONS_DATA` และใช้ค่าของประกาศแทนเมื่อมีข้อมูล
เมื่อไม่มีประกาศราคาจึงยังปรากฏ แต่ผู้ใช้แยกไม่ได้ว่าค่าไหนเป็นข้อมูลสำรอง
แนวทาง: แสดงที่มา วันเวลา จำนวนประกาศที่ใช้ และสถานะ “ข้อมูลตัวอย่าง/ไม่มีข้อมูลล่าสุด”
แยกแต่ละ metric ให้ชัด ไม่สรุปว่าตัวเลขบนการ์ดกับรายละเอียดขัดกัน เพราะเป็น buy/sell คนละค่า
ไฟล์: `src/app/page.tsx:1729`, `1745`, `1755`, `3073`, `3150`

**U05 · โหลดประกาศผิดพลาดแล้วไม่มีสถานะ recovery — ยืนยันจากโค้ด**

posts เริ่มด้วย `INITIAL_POSTS`; fetch ที่ไม่สำเร็จไม่แสดง error หรือ retry
จึงเสี่ยงแสดงข้อมูลเดิม/ตัวอย่างโดยไม่บอกผู้ใช้ว่าโหลดข้อมูลจริงไม่ได้
แนวทาง: แยก loading, success-empty, error และ stale data พร้อมปุ่มลองใหม่
ไฟล์: `src/app/page.tsx:831` และ `959`
ยังไม่ได้บังคับ API นี้ให้ล้มเหลวบน session สมาชิกจริง จึงไม่จัดเป็น browser-reproduced finding

**U06 · Admin แยก network/server failure จากหมดสิทธิ์ไม่ได้ — ยืนยันจากโค้ด**

`checkAdminAuth` ตั้ง authenticated เป็น false ทั้ง non-OK ทุกชนิดและ catch
ปัญหาเครือข่ายจึงอาจนำผู้ใช้กลับหน้า login ทั้งที่ session ยังใช้ได้
แนวทาง: แยก 401/403 จาก 5xx/network พร้อม retry ที่รักษาบริบทงาน
ไฟล์: `src/app/admin/page.tsx:175`
ไม่ได้บังคับ offline ใน session แอดมินจริง; offline ที่ทดสอบจริงเป็นหน้า login ผู้เยี่ยมชม

### P3 — ความสม่ำเสมอและความเรียบง่าย

- ทำคำศัพท์และภาษาไทย/อังกฤษให้สม่ำเสมอ เช่น title ที่มีคำอังกฤษยาวบนมือถือ
- หน้าแรกส่วนประกาศล่าสุดควรมี empty state ที่ช่วยไปต่อเมื่อไม่มีรายการ
- ลด icon/emoji ตกแต่งที่ไม่ช่วยตัดสินใจ และเพิ่มภาพประกาศเฉพาะเมื่อมีข้อมูลภาพจริง
- quick reply ปัจจุบันเรียกส่งข้อความทันทีตามโค้ด ไม่ได้ทดลองกด
  ควรให้ผู้ใช้คาดเดาได้ว่าจะส่งทันทีหรือเติมลงช่องพิมพ์ (`src/app/page.tsx:4410`)

## ส่วนที่ทำได้ดี

- มี token สีทั้งสองธีม ปุ่มหลักและข้อความหลักมีคอนทราสต์คำนวณได้ดี
- dialog ลงประกาศมี labels, scroll, Escape และการคืน focus ที่เห็นได้จริง
- dialog บัญชีมี focus outline ระหว่างทดลอง Tab; ภาษาอยู่ในเมนูบัญชีบนมือถือ
- หน้า register ใช้ radio ที่โปรแกรมอ่านได้สำหรับบทบาท และจัดฟอร์มแนวตั้งบนมือถือ
- login ฟอร์มว่างถูกบล็อก; network error มีข้อความให้ลองใหม่และไม่ล้างข้อมูลที่กรอก
- ระบบ support มี loading/empty state และมี polling ใน component ของตนเอง
- login ที่ zoom 200% ยัง reflow และเลื่อนอ่านฟอร์มได้ในส่วนที่ตรวจ

2. แก้ U03/U04/U05/U06: คะแนนไม่มีรีวิว, ป้ายที่มาราคา, loading/error/retry และ auth errors
3. ทำตัวกรอง/empty states ให้กระชับและช่วยผู้ใช้ไปต่อได้จริง
4. แก้ accessibility และภาษา: send label, selected states, tap targets, placeholder และ error translation
5. ตรวจซ้ำทุกหน้าที่เปลี่ยนบน 320/390/768/1440 ทั้ง light/dark และ keyboard;
   ทดสอบคำสั่งจัดการข้อมูลในฐานทดสอบแยกเมื่อได้รับขอบเขตที่ชัดเจน

ไฟล์เป้าหมาย: `src/app/page.tsx`, `src/app/admin/page.tsx`,
`src/app/globals.css`, `src/components/theme-switcher.tsx`,
`src/components/listing-card.tsx` เมื่อยืนยันการเพิ่มภาพ/ลำดับข้อมูล,
และ component แอดมินใหม่หากจำเป็นต้องแยก mobile summary
ไม่จำเป็นต้องเปลี่ยน schema หรือกฎการหักคะแนนเพื่อแก้ปัญหา layout
ความเสี่ยงหลัก: shared styles กระทบหลายหน้า และ UI คำสั่งแอดมินต้องรักษาค่า payload/authorization เดิม

## ข้อจำกัดที่ยังต้องตรวจแยก

- ไม่ได้ทดสอบบนเครื่อง iOS/Android จริง, virtual keyboard, NVDA/VoiceOver หรือ gesture บนอุปกรณ์จริง
- ไม่ได้ทดสอบทุกหน้าในทุก combination ของขนาด ธีม ภาษา และข้อมูล
- ไม่ได้ทำ Lighthouse/Core Web Vitals, load test, security audit หรือ pixel contrast scan ทั้งหน้า
- ไม่ได้ทดสอบการลงประกาศ/ส่งข้อความ/ปิดดีล/รีวิว/ลงโทษ/ลบข้อมูลครบวงจรในฐานจริง
- ไม่ได้จบ OTP/สมัคร/กู้รหัสผ่านจริง และยังไม่ยืนยันหน้า detail ของประกาศครบทุกสถานะ
- tests role เดิม 7 ข้อตามบันทึกเก่าไม่ได้รันหรือแก้ในรอบนี้

จึงสรุปได้ว่า “ตรวจหลายหน้าหลายขนาดและพบรายการแก้ที่มีหลักฐาน”
ไม่ใช่ “ทุกอย่างผ่าน” หรือ “ตรวจครบทุกเงื่อนไขแล้ว”
