# ประวัติแชตและศูนย์ช่วยเหลือ

## หน้าศูนย์ช่วยเหลือ

เปิดเมนูบัญชี → “ศูนย์ช่วยเหลือ / ติดต่อแอดมิน” เพื่อเลือกรายการที่เคยสนทนา รวมรายการที่ปิดดีลและแชตในประวัติ การ์ดแสดงชื่อประกาศ คู่ค้า รหัสห้อง วันที่เริ่มสนทนา และสถานะคำร้อง พร้อมโหลดรายการเพิ่มเติม

เลือกการ์ด → เลือกหัวข้อปัญหา → พิมพ์รายละเอียด → ส่งคำร้อง จากนั้นเปิดบทสนทนาและคิวของรายการนั้น หากมีคำร้องอยู่แล้วจะเปิดเรื่องเดิม ข้อความต้อนรับเป็นข้อความแนะนำของระบบ ไม่ได้เชื่อม AI ตอบอัตโนมัติ

ปุ่มติดต่อแอดมินในหัวห้องแชตเข้าไปที่รายการนั้นโดยตรง กดลูกศรกลับเพื่อดูรายการอื่นได้ ใช้สี/ฟอนต์/theme ของ Durian Hub ทั้ง desktop/mobile ตัวอย่างและผลทดสอบ: [support-ui-preview](support-ui-preview/README.md)

## คิวรับเรื่อง

- คำร้องใหม่อยู่ใน “รอตรวจสอบ” เรียงตาม `queuedAt` เก่าสุดก่อน และใช้ id ตัดสินเมื่อเวลาเท่ากัน
- ผู้ใช้เห็นจำนวนเรื่องที่รอก่อนตนเอง อัปเดตพร้อมบทสนทนาทุก 5 วินาที จำนวนนี้นับเฉพาะเรื่องที่ยังไม่มีผู้รับ ไม่ใช่เวลาประมาณการแก้ไขเสร็จ
- แอดมินกด “รับคิวถัดไป” เพื่อรับเรื่องเก่าสุด ระบบใช้ transaction และตรวจสถานะป้องกันการรับเรื่องซ้ำ หากมีการรับพร้อมกันอาจตอบ 409 ให้ลองอีกครั้ง
- เรื่องที่รับแล้วแสดงชื่อผู้ดูแล เฉพาะผู้ดูแลเรื่องนั้นตอบและปิดเรื่องได้ แอดมินคนอื่นยังอ่านข้อมูลได้
- แอดมินรับเรื่องถัดไปได้แม้มีเรื่องที่กำลังรอผู้ใช้ตอบ ไม่ต้องปิดเรื่องเดิมก่อน
- ส่งรายละเอียดเพิ่มไม่เปลี่ยน `queuedAt` ส่วนผู้แจ้งเปิดเรื่องซ้ำจะล้างผู้รับ/ผลแก้ไขปัจจุบันและเข้าท้ายคิวใหม่ โดยผลแก้ไขเดิมยังอยู่ในประวัติข้อความ
- หน้าแอดมินแยก “รอตรวจสอบ / กำลังดำเนินการ / แก้ไขแล้ว” รีเฟรชรายการทุก 10 วินาที

### อัปเกรดฐานข้อมูลที่มีระบบช่วยเหลือแล้ว

ใช้ `database/support-queue.sql` ครั้งเดียวหลัง schema จาก `chat-support.sql` พร้อมแล้ว ไฟล์นี้เพิ่ม `queued_at`, backfill จาก `created_at` และเพิ่ม index สำหรับคิว สำรองฐานข้อมูลและหยุดเว็บก่อนทำ

หาก `db push` เพิ่มคอลัมน์/index แล้ว อย่ารัน ALTER/CREATE ซ้ำ ให้ตรวจ schema และทำเฉพาะ UPDATE backfill ก่อนเปิดใช้คิว ฐานข้อมูลที่ติดตั้งใหม่จาก Prisma schema ล่าสุดมีคอลัมน์ครบอยู่แล้วและไม่ต้องรันไฟล์อัปเกรดทั้งสองซ้ำ

- นับเวลา 168 ชั่วโมงจาก `ChatRoom.closedAt` ที่บันทึกขณะยืนยันดีล ไม่ใช้เวลาข้อความล่าสุด
- เมื่อครบกำหนด ห้องย้ายไปแท็บประวัติและ API ปฏิเสธการส่งข้อความของทั้งสองฝ่าย ข้อความและข้อตกลงยังอ่านได้
- ห้องอื่นของประกาศที่ปิดขายแล้วใช้เวลาปิดเดียวกับประกาศ แต่ยังคงสถานะ ARCHIVED เพื่อไม่แสดงว่าเป็นคู่ค้าที่ปิดดีลสำเร็จ
- การเข้าประวัติคำนวณเมื่ออ่านข้อมูล ไม่ต้องใช้ cron และไม่ลบข้อมูล
- ศูนย์ช่วยเหลือเปิดได้จากทุกห้อง รวมประวัติ: หนึ่งคำร้องต่อผู้แจ้งต่อห้อง ผู้แจ้งอีกฝ่ายมองไม่เห็นคำร้องนี้
- ผู้ดูแลเปิดหน้าแอดมิน → ศูนย์ช่วยเหลือ เพื่อดูรายการ รับเรื่อง ตอบผู้แจ้ง ตรวจหลักฐาน และปิดเรื่องพร้อมผลแก้ไข ผู้แจ้งเปิดเรื่องซ้ำได้
- การเปลี่ยนสถานะถูกบันทึกเป็นข้อความพร้อมผู้ดำเนินการ ผู้แจ้งส่งข้อความต่อเมื่อเรื่องยังเปิดเท่านั้น
- กดรีเฟรชเพื่อดูคำร้องใหม่ ส่วนข้อความของคำร้องที่เปิดอยู่รีเฟรชทุก 5 วินาที

## ฐานข้อมูลเดิม

โปรเจกต์นี้ยังไม่มี Prisma migration baseline จึงเตรียม SQL สำหรับอัปเกรดฐานข้อมูลเดิมไว้ที่ `database/chat-support.sql` แทนการเริ่ม migration history ที่ไม่ตรงกับฐานข้อมูลจริง

1. สำรองฐานข้อมูลและหยุดรับคำขอเขียนระหว่างปรับ schema
2. ใช้ `database/chat-support.sql` **หนึ่งครั้ง** กับฐานข้อมูลเดิม ก่อนเปิดแอปเวอร์ชันใหม่ SQL ใช้ ALTER/CREATE ซึ่ง MySQL ไม่รับประกัน rollback ทั้งชุด จึงต้องตรวจ schema ก่อนรันซ้ำหากเกิดข้อผิดพลาด
3. SQL เติม `closed_at` จาก `created_at` ของดีล ACCEPTED/COMPLETED/DISPUTED ที่เก่าที่สุดของประกาศ ไม่ใช้เวลาข้อความและไม่สร้างเวลาเดาให้ห้องที่ไม่มีหลักฐานดีล
4. ตรวจรายการห้องที่ยังไม่มี `closed_at` จาก SELECT ท้ายไฟล์และแก้ตามหลักฐานจริง ห้องที่ไม่มีเวลาอ้างอิงจะยังไม่ถูกล็อกตามอายุ
5. Generate Prisma Client และ build แอปเวอร์ชันใหม่ก่อนเริ่มบริการ หลีกเลี่ยง entrypoint เดิมที่ seed ทุกครั้งหากเป็นฐานข้อมูลใช้งานจริง

ฐานข้อมูลใหม่ใช้ schema Prisma ปัจจุบันได้โดยตรง ส่วนฐานข้อมูลที่ใช้ `db push` เพิ่มคอลัมน์/ตารางแล้ว ต้องรันเฉพาะ UPDATE backfill และ SELECT จากไฟล์ SQL ไม่รัน ALTER/CREATE ซ้ำ

## การตรวจสอบ

`tests/chat-support.test.cjs` ตรวจขอบเขตเวลา 7 วัน, API ห้ามส่งในห้องหมดเวลา, สิทธิ์เจ้าของคำร้อง, การป้องกันปลอมเป็นแอดมิน, การปิดเรื่องพร้อมผลแก้ไข และเปิดเรื่องซ้ำ ใช้ DB/auth mocks เพื่อไม่แก้ข้อมูลจริง

การเปลี่ยนแปลง source ไม่ทำให้บริการ Docker เดิมอัปเดตโดยอัตโนมัติ ต้องปรับฐานข้อมูลและ rebuild/redeploy ให้สอดคล้องกัน
